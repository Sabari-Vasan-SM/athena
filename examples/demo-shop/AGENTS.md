## Athena Project Intelligence

This project maintains structured project knowledge in `.athena/` (generated by Athena, curated by the developers).

Before making significant changes:

1. Read `.athena/rules.md` and follow every enabled rule (lines marked `[disabled]` do not apply).
2. Classify the task and read only the relevant Athena documents (see the relevance map below).
3. Identify the affected modules and architecture boundaries.
4. Check security implications (`.athena/security.md`, `.athena/auth.md`) when touching input handling, auth, data access or secrets.
5. Check database and API implications when the change touches schema, queries or endpoints.
6. For non-trivial work, state a short implementation plan before editing.
7. Implement only the required changes.
8. Run the relevant validation (tests, lint, type checks — commands are listed in `.athena/project.md` and `.athena/testing.md`).
9. If you changed project structure, dependencies, routes, schema or infrastructure, run `athena sync --dry-run` to see which knowledge is affected, and tell the developer to review it with `athena sync` (apply it yourself only if permitted).

### Relevance map

| Task type | Read from `.athena/` |
| --- | --- |
| Database / schema / migrations / queries | `database.md`, `architecture.md`, `api.md`, `security.md`, `testing.md`, `rules.md` |
| API endpoints / controllers / request handling | `api.md`, `auth.md`, `security.md`, `architecture.md`, `testing.md`, `rules.md` |
| Authentication / authorization / sessions / permissions | `auth.md`, `security.md`, `api.md`, `database.md`, `testing.md`, `rules.md` |
| Frontend UI / styling / components | `project.md`, `architecture.md`, `rules.md` |
| New feature spanning multiple layers | `project.md`, `architecture.md`, `database.md`, `api.md`, `auth.md`, `security.md`, `testing.md`, `rules.md` |
| Bug fix / debugging | `debugging.md`, `architecture.md`, `testing.md`, `rules.md` |
| Performance work / caching / background jobs | `performance.md`, `architecture.md`, `database.md`, `rules.md` |
| Tests | `testing.md`, `project.md`, `rules.md` |
| Build / CI / Docker / deployment / infrastructure | `deployment.md`, `project.md`, `security.md`, `rules.md` |
| Dependency changes | `project.md`, `security.md`, `rules.md` |
| Code review | `code-review.md`, `rules.md`, `security.md`, `testing.md` |
| Small, local change (typo, rename, copy) | `rules.md` |

For small, local changes (typos, copy, a rename inside one file) reading `rules.md` is enough — do not load every document.

Athena knowledge labels every statement as `FACT`, `DETECTED`, `INFERRED` or `UNKNOWN`. Treat `INFERRED` and `UNKNOWN` as unverified — confirm in code before relying on them. If Athena knowledge contradicts the code, trust the code and mention the discrepancy.
